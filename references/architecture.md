# 架构提炼：多模块交易后台

## 模块关系

```text
用户端 / 管理端 API
          │
JWT 拦截与身份上下文
          │
Server：Controller → Service（事务与规则）→ Mapper / 外部适配
          │                         │
          ├─────────────────────────┴───────────┐
          │                                     │
Common：结果、异常、配置、横切能力      POJO：Entity、DTO、VO
          │
数据库 / Redis / 支付 / 对象存储 / WebSocket
```

## 交易约束

| 主题 | 设计要点 | 常见失误 |
| --- | --- | --- |
| 身份与角色 | 用户端、管理端使用不同路由与权限策略 | 仅靠 URL 前缀而不验证资源归属 |
| 订单状态 | 每次迁移有前置状态、操作者、时间和幂等语义 | 在控制器里任意更新状态字段 |
| 金额与库存 | 服务端重新计算或校验，不信任客户端金额 | 用前端传值直接创建支付金额 |
| 数据报表 | 查询范围、指标口径、时区和空数据有明确契约 | 把 CSV 字符串当成唯一报表模型 |
| 外部系统 | 适配器负责超时、重试边界和错误映射 | 在领域逻辑中直接调用 SDK |

## 上线检查

1. 敏感配置通过环境或密钥管理注入，绝不提交支付凭据、签名材料或对象存储密钥。
2. 每个写操作都有鉴权、参数校验、事务/幂等策略和结构化审计记录。
3. 报表查询设日期范围上限和索引策略；导出对大数据量使用异步或流式方案。
4. 用户可见错误和内部异常日志分离，支付回调与订单更新可重复安全执行。
